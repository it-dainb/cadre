# Profile

A profile is the workflow as data: the types of task and their pipelines, the steps (a role that works, or a gate that checks), the roles with their tools and report forms, the checks, the flags a person answers, the delivery hooks and the landing provider. cadre 2.0 ships three: `default` (plan, test first, build, review, land), `docs` and `analysis`. The engine reads the profile through one interpreter; nothing in core names a step, a role or a test tool.

Choose one with `profile` in `~/.claude/cadre.json` (a built-in name, or an inline profile) or in `.cadre/config.json` (a name). `/cadre profile` shows the active profile and which layer each section comes from.

## Layers

| Layer | Source | May set |
|---|---|---|
| built-in | `profiles/default.ts`, `docs.ts`, `analysis.ts` (data consts) | everything |
| user | `~/.claude/cadre.json`: `profile`; the only home of `adapters` and `credentialEnv` | everything else |
| repo | `.cadre/config.json` (`profile` name, `limits`, `units`, `sync`) and an optional `.cadre/profile.json` with `.cadre/modules/*.mjs` | everything the user layer may set, except `adapters` and `credentialEnv` |

Merge is per section and per key, built-in then user then repo, and the repo wins: a key replaces the same key below it, keys it does not name survive, scalars and arrays replace whole. A layer that names only some sections inherits the rest (`docs` and `analysis` inherit the default's flag rows). The profile loads once at session start and is fixed for the session; an edit takes effect in the next one. An invalid repo profile (parse error, unknown key, missing module, a user-only key) makes cadre dormant for that repo; Doctor and `/cadre profile` still show the line. A repo profile runs with your permissions: see [limitations](limitations.md).

## Sections

The schema is closed: an unknown key is a refusal with a one-line example.

| Section | What it holds |
|---|---|
| `schema` | always `2` |
| `types` | per task type: `pipeline` (step ids), optional `lite` pipeline, `acceptance` (`format` text, `cover`: `results`, `report` or `none`), `contract` (`required`, `none` or `{schema}`), `rubric`, `branch` prefix, `commit` prefix |
| `steps` | a role step (`role`, `workspace` `none`, `worktree` or `view`, `brief` sections, `locks`, `onFail`) or a gate (`gate`, `expect` `pass` or `fail`, `on` an earlier step, `onFail`) |
| `roles` | description, `prompt`, `tools`, `network`, `write` globs, `ttl`, `onSilent`, `nudge`, `report` (outcomes, fields with caps, required, `requiredWith`, `ask`, `eg`), optional `verdict`, `rubric`, `routing` by risk |
| `checks` | a named slot: `failExit` codes, `network`, `timeoutS`. Slots hold no argv: a unit names its argv in `units[].checks` |
| `flags` | per flag kind: `why`, `holds`, `yolo` (`main` or `human`), and the `options` a person or main chooses, each a list of effects from a closed set |
| `hooks` | per event (`task.closed`, `epic.landed`, `release`): a role or a `run` argument list with an optional `commit` template and `envPass` |
| `landing` | `provider` (`direct` or a module), `onEpicDone`, `prepare`, `suites`, `baseline`, `union`, `args`, `envPass` |
| `protected` | globs task agents may not change (the default: `CHANGELOG.md`); core adds `.git/ .cadre/ .claude/ .mcp.json` |
| `sandbox` | `env` set in every check and tester run |
| `fields` | the task fields a plan call may carry, each `required` (true, false or a list of types) and optionally a `kind` (`bool`, `ids`, `{enum}`) |
| `limits` | engine counters: `reportRetries`, `shapeRetries`, `nudges`, `stagnantNudges`, `silentRuns`, `startFails`, `limitWaitMinutes`, `rebaseRounds`, `specAccepts` |

`${NAME}` is the one substitution, over a closed set (`MODULES TMPDIR UID WT PATH id title version`), in `sandbox.env` values, hook argument lists and commit templates. An unknown name is a refusal. `${MODULES}/x.mjs` names a file in the plugin's `modules/` (or, in a repo profile, in `.cadre/modules/`).

`${title}` and `${id}` come from agent and tracker text: never put them inside `sh -c` or any other shell string; a hook argument list passes them as plain arguments.

### Steps and `onFail`

`onFail: {retry, then}` counts differently for the two things a failing step can do:

- `then: {"back": "<step>"}` (a judge, such as the reviewer): the work is sent back `retry` times and the next failure raises the flag. With `retry: 3` it goes back three times and the fourth failing verdict raises `rework`.
- `then: "human"` (a gate such as the tester's red): the failing round itself counts, so the `retry`-th failing round raises the flag. With `retry: 3` the third refused red raises it.

`then: "cancel"` ends the task. A gate with no `onFail` (the default's green) only refuses the worker's report, without a count.

A read-only step (a role with `workspace: "none"` and no `verdict`) may be followed only by a role step or the `report` gate: no tree is left to check, so the loader refuses a check or integrate gate right after it.

## Gate contract

A gate runs the unit's argv for the named check slot in the jail, with `CADRE_JUNIT` set to a path core allocates for that run, and reads two things only: the exit code and, if the runner wrote it, a JUnit XML file at `$CADRE_JUNIT`. Output text is never parsed; the agent gets the last lines of it as data. A runner that writes JUnit gets per-test verdicts; one that does not is judged by its exit code alone. `/cadre init` has the agent pick each unit's `test` argv so it writes JUnit, then runs it once to record whether it does (B18).

| Verdict | When |
|---|---|
| `error` (the check is broken, never a red: flag `gate-error`) | timeout; an exit outside `0` plus the slot's `failExit`; a JUnit file that is malformed, has a DOCTYPE or breaks the size limits; under `expect: fail` with declared tests, no results file |
| `expect: fail` is ok | exit in `failExit`; with results: no per-test error, at least one failure, every declared test name present, and no passing test whose ids are not "already holding" |
| `expect: pass` is ok | exit `0`; with results: no failure or error, every declared name present |
| no results, no declared tests | exit code only; "Already holds" is not offered; `cover: results` falls back to the reviewer's coverage list |

A test that errors instead of failing is not a red: the tester makes it compile and run (B1). A test command is adopted as the unit's `test` check only after a structural red: valid JUnit with the declared tests failing (B19). Common runners:

| Runner | JUnit |
|---|---|
| node:test | `--test-reporter=junit --test-reporter-destination=$CADRE_JUNIT` |
| vitest | `--reporter=junit --outputFile=$CADRE_JUNIT` |
| jest | `jest-junit` (`JEST_JUNIT_OUTPUT_FILE`) |
| pytest | `--junitxml=$CADRE_JUNIT` |
| Maven, Gradle | surefire or the `test` task XML under `target/surefire-reports` or `build/test-results` (copy it to `$CADRE_JUNIT`) |
| Go | `gotestsum --junitfile $CADRE_JUNIT` |
| Rust | `cargo nextest` with `[profile.ci.junit] path` |
| .NET | `dotnet test --logger "junit;LogFilePath=$CADRE_JUNIT"` |
| PHP | `phpunit --log-junit $CADRE_JUNIT` |
| Ruby | `rspec -r rspec_junit_formatter --format RspecJunitFormatter -o $CADRE_JUNIT` |
| C and C++ | `ctest --output-junit $CADRE_JUNIT` |

A runner with no JUnit reporter pipes through a converter or is exit-only. The reader is `core/junit.ts` over the vendored `@xmldom/xmldom` (MIT).

## Task fields

`fields` decides what a plan call may carry beyond the engine's own arguments (`type`, `acceptance`, `contract`, `lane`, `risk` and the plan arguments). The plan rules, the planner's brief and the lite lane's line are generated from it, so a profile that declares no `changelog` is never told to send one and refuses it as an unknown field. `package`, `scope` and `breaking` are always allowed (the engine reads the unit and the commit message from them). `lane` picks the pipeline; `risk` (`light`, `standard`, `thorough`, `core`) routes models and review depth, and an absent `risk` is `standard`.

## The three profiles

Each is data you can copy into `.cadre/profile.json` or an inline `profile` and edit. `docs` and `analysis` list only the sections they replace; the rest comes from the default.

## What changed from 1.0.1

Every intended difference, by row. Anything else a transcript shows is a bug.

| # | 1.0.1 | 2.0 |
|---|---|---|
| B1 | an `<error>` test (it imports a symbol that does not exist yet) counted as red | a per-test error is not red: the tester makes it compile and run |
| B2 | a unit with `runner: text` read its tests from output text | the field is gone; a unit without JUnit results is exit-only, or `gate-error` with declared tests |
| B3 | a missing runner was detected from output text and blocked with setup text | exit 127 or any exit outside `0` plus `failExit` is `gate-error`; an import failure with declared tests and no results is `gate-error`, never a false red |
| B4 | `accept:` / `reject:` text prefix decided a flag | the option's `choice` key only |
| B5 | installs by helper (`request` outcome) | the agent installs itself; no replay after a spec reset |
| B6 | changelog entries amended into the epic merge commit | one `docs(changelog)` commit per closed task on the epic branch, by a hook, or none |
| B7 | submodule landing | refused with one line |
| B8 | the built-in PR mode read `gh pr checks` text | the `landing-gh` module reads `gh pr view --json statusCheckRollup` |
| B9 | risk scored from diff size and labels | the planner-declared `risk` |
| B10 | duplicate-task detection by title | gone |
| B11 | lane chosen by task count | the planner-declared `lane`, a person can override |
| B12 | `lite+tdd` lane | gone: lite means lite; a bug that needs a test first goes in the full lane |
| B13 | branch prefix by conventional commit type | the type's plain `branch` prefix |
| B14 | `tdd.collectErrors` and `units[].tdd.report` | gone; core allocates `$CADRE_JUNIT` |
| B15 | Given/When/Then enforced by regex, `S<n>` ids | `{id, text}` items, any id |
| B16 | config keys `types`, `tdd.*`, `review.*`, `roles.custom`, `lanes`, `suites`, `changelog`, `release`, `landing.review/remote`, `units[].setup` | the profile, `units[].checks.setup` and `landing.*`; clean break |
| B17 | `flag.resolved` emitted by hand on some paths | emitted once per flag that left the target |
| B18 | `/cadre init` ran nothing | init runs each unit's `test` check once in its jail |
| B19 | adoption of a test command also took text runners | adoption needs a structural red |
| B20 | sync ran in core on the tick | `modules/sync.mjs`, one process per due unit, at most one run per unit per 30 s unless a task transition wakes a target |
| B21 | an adapter inherited the session environment | adapter, hook, provider and module get an environment allowlist (hygiene, not a boundary) |
| B22 | Doctor pinged every adapter | Doctor shows the last module result and its age |
| B23 | a repo profile was a name and numbers | a repo may ship `.cadre/profile.json` and modules, loaded as they are (accepted risk) |
