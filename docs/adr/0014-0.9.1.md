# ADR 0014: 0.9.1

## Task store in .cadre/store
- Every bd call carries `BEADS_DIR=<repo>/.cadre/store` (`adapters/beads/layout.ts` `dirOf`; `Bd` adds it to the env). Probed with real bd 1.3.1: `bd init` under BEADS_DIR puts the store there and writes no `.beads` at the root; it needs `.cadre/` to exist, and drops `.cadre/store.gate.lock` beside the store (both excluded in `.git/info/exclude`; bd also writes a root `.gitignore`, as before).
- Legacy: no `.cadre/store` but a `.beads` → no BEADS_DIR, bd finds `.beads` itself. Never moved automatically: doctor shows a row and a card (`init:92`, answered through `setup confirm`); the move (`moveStore`) refuses while a task is active or in review, `mv`, re-probes, rolls back on failure, then adds the exclude lines.
- Fence and effect check need no change: `.cadre/` is already protected (`PROTECTED`, `STATUS` exclude, L2 denyWrite on the repo). `.beads` stays listed for legacy repos.
- Tests: `tests/store-layout.test.ts`; real bd: `tests/dev/store-dir.mjs`.

## Onboarding: init folded into the first goal, preferences, one message state machine
User decisions, 2026-10-12 (plan `cadre-0.9.1` A, B, E).

### Init folded into `/cadre <goal>`
- In a dormant repo (no `.cadre/config.json`) `/cadre <goal>` and `/cadre yolo <goal>` (composer only) ask ONE decision `init:goal`: "cadre isn't set up here. Set it up and plan this goal?" (Set up = `init goal`, Not now = `init cancel`). Typing the goal is the per-repo opt-in; the dialog is the consent to change the repo. The goal and its mode (yolo, or `drive.mode` from the user layer) wait in `ui.onboard`.
- Set up starts the ordinary visible init run (`agentrun.start(h, 'init', goal)`, `secret.run.goal`) with a brief that says the goal comes next and to skip the mission question. The mission check is ok in a goal run ("you approve it with the plan"); everything else is checked as before, and the safety settings keep their own confirm (security: never bundled with anything).
- When every check passes, the run ends WITHOUT its "all done" card and `lanes.goal(h, text, mode)` queues the goal brief: auto/yolo carry over exactly as typed. The run checklist stays quiet in a goal run, so the human sees exactly three dialogs: Set up, safety settings, mission + plan.
- Mission + plan in one dialog: when no mission is recorded, the goal brief says "There is no mission yet." and `guides/goal.md` tells main to put `metadata.mission` ("Goal: …\nConstraints: …\nNon-goals: …") on the plan's TaskCreate (validated: string, plan only, ≤ 1000). It lives in epic meta `cadre.mission`; `dispatch.redraw` titles the decision "approve the mission and plan <id>", shows `mission: <goal>` as the first line and includes it in the content hash; the first approve records it (`store.record('mission')`, `board.mission`) and clears the meta. A rejected plan records nothing; the next goal asks again.
- `/cadre init` stays for deliberate re-runs (README lists it as such, not in the quick start). A machine without a setup stamp gets the welcome line instead of the dialog.
- Rejected alternative: a second "mission" dialog before the plan (0.9.0's init) — two approvals for one intent.

### Preferences (setup phase 5)
- Main asks with AskUserQuestion (mode auto|yolo, turns, $, minutes) and hands the answers over with one `TaskCreate {kind:"preferences", …}`. TaskCreate is the only structured channel main has to cadre that also works in a dormant repo, so `commands/prefs.prefsCall` answers it in tool.call slot 5 before the guards (only during a setup run; anything else is denied with the next step).
- cadre, never Claude, writes `~/.claude/cadre.json` (it holds S keys such as `drive.mode`): a diff on card `init:93`, Confirm → re-plan must match the card (else "changed since you saw it", nothing written), `.bak`, write through `DRIVE.humanWrite` (a running drive takes the human's change as its baseline), re-read. Only keys that differ from the defaults are kept; choosing a default removes the key; nothing to change → no card. Done = `$.store cadre:prefs` (setup checklist row "preferences"). Doctor row: `your preferences: ~/.claude/cadre.json|the defaults (mode …, limits turns/$/minutes)`.

### One message state machine
`commands/cadre.status(h)`: the reply of bare `/cadre` (which also opens the pane) and of every typed command that does not apply in a dormant repo. States, first match: dormant + no setup stamp → `Welcome to cadre · run /cadre setup once on this machine` (a set-up repo implies a set-up machine, so harness and eval repos never see it) · dormant → `Ready when you are · /cadre <goal> to start · /cadre yolo <goal> to run it without questions` · a decision waits → `<plan> · N needs you · press 1 to answer` · no open plan → `No plan yet · /cadre <goal> to start` · approved, drive off, no live binding → `Unfinished plan <id> <slug> (d/n) · /cadre continue to pick it up` · else `<id> <slug> · d/n done · running <task> <step> · /cadre to open`. The band keeps showing only "needs you" and the plan line (an untouched repo draws nothing); the pane's dormant body says the Ready line. "cadre is off in this repo · run /cadre init" is gone everywhere (`BUDGET.offText`, tests/onboard.test.ts).

### Known red before the goal, the setup commit, parallel preferences (team decisions, live runs)
- A goal run treats a check that is red on the clean checkout as **known red**, not as an init failure: often the failing test IS the bug the goal fixes, and the only other ways out (drop the check, weaken the test) are worse. The safety card shows `known red before your goal: <root>: <check> · it must turn green`, so the human confirms it knowingly; Confirm grants `packages[].knownRed` in the user layer (`repos[<repoKey>].packages`, the only layer that may grant it). The check keeps running: the fix task's green gate requires it (verify defaults to `test`), integration runs it without gating, and a landing where it passes removes the mark (`commands/init.clearKnownRed`, `.bak`, through `DRIVE.humanWrite`) and records a decision. Never skipped, never weakened.
- After the safety confirm cadre commits `.cadre/config.json` and the changelog (`chore: set up cadre`, under `git.op` so its own ref move is not a flag) and fast-forwards the other of main/dev when it is behind. Claude never commits there (a protected-ref move by main is a flag); without the commit a clone has no config and a release is refused (no changelog on dev).
- Setup preferences also ask tasks in parallel per plan (`maxParallel`: 1 · 3 · 5 · unlimited, default 3) and plans in parallel per milestone (new `milestone.maxEpics`, class O, default 2, stored for the milestone lane). Unlimited = 0 = no cadre cap (admission skips the cap; drive bounds still apply); the card then adds "every parallel task is a full Claude agent: cost and load grow; drive limits still apply".

## Continue after exit

### Why
Quitting Claude Code (or a crash) mid-plan left the plan stranded. The next session re-adopted the pointer as if it were a `/clear`: it moved the dead agents' bindings to itself, heartbeat their claims forever and re-armed drive, which then waited on agents that no longer existed. Any rebind waited for the 5-minute claim to lapse, and that lapse never came because the new session kept renewing it.

### Decision
- **A `/clear` is not a quit.** The pointer records the process (`proc`, a module-level id; `$.state` and the session id reset on `/clear`, the process and its agents do not). Same process: as before, bindings and drive go on. Another process: the plan, tasks and pending decisions come back, but no binding is adopted and drive is not re-armed. `ui.cont` makes the band offer **`0: continue`**; the resume line says `/cadre continue or 0 picks it up`. Nothing restarts by itself.
- **One key, one meaning per state.** The band's drive key stays `0`: `stop` while drive runs or waits on a gate, `resume` when it stopped, `continue` when an earlier session left an approved plan and nothing drives it (`ui/v2/facts.driveOf`, `drive continue` is the press).
- **`/cadre continue`** (`core/session.continueRun`, `ROUTES.continue`; typed or the band press) re-adopts the plan (pointer, else the newest unfinished epic), refuses when another live session drives it, takes over the drive record in its stored mode, budget and baseline (a hard stop that happened meanwhile, e.g. yolo without contained agents, still stops it; a drive record that is off is armed in the plan's mode), and for each in-flight task (active, or review at the reviewer step) whose owner session is gone: drops the binding, records this session as the owner, clears a gone reviewer's `owner`, and queues one brief for main (`spawn TASK-<id> (it starts from its last checkpoint)` / `(reviewer)`). Main's spawn goes through admission's rebind, which commits the dirty tree as `wip(<id>): checkpoint` and hands the new agent the checkpoint, the diff since the spec/base, the last failing check (`cadre.lastCheck`, written by `runCheck`) and the decisions. One reply line: `Picking up a2 worker · drive auto · p3 auth 4/7 done`. Nothing open: `nothing to continue · /cadre <goal> to start`.
- **Stale at once, never stolen.** Each active session stamps `cadre:<repo>:alive[session] = {proc, at}` every 10 s from the tick; a task's owner session is in `cadre:<repo>:hb:<id>` (`{s, at}`, written at spawn and at each heartbeat). `held(owner)`: `here` (this process), `other` (another process stamped in the last 30 s, or an unknown owner), `gone`. Rebind refuses a live claim only when its owner is `other`; `/cadre continue` skips those tasks (`… stay with another session`). Across machines the store's assignee still fences (unchanged).
- **What a quit can lose:** only what was not on disk: the agent's in-flight reasoning and a tool call cut mid-way. Every file the worker wrote is in its worktree and becomes the wip checkpoint at the respawn. (A worker's turn ends only when it stops, so the turn-end checkpoint does not cover a quit; the rebind's checkpoint does.)

### Found on the way (live)
- bd drops the claim lease when a task moves to review, so the lease is no test for "an agent may still be working": after a `/clear` the prune (re-run by `wake`) deleted the live reviewer's pointer binding and its report was refused (`no task is bound to this agent`); resumes to a reviewer in review were skipped too. Bindings, the prune and the resume sender now test the task state (`inFlight`: active, review, blocked).
- A hook arriving during the seconds-long rehydrate (the reviewer's report right after `/clear`) saw a half-built board: `rehydrate` is now single-flight.
- A board rebuilt in a new session has no start time; the band showed `497720h35`. No counter is shown instead.

## G: conflicts between parallel tasks in one plan
User decisions, 2026-10-12 (plan `cadre-0.9.1` G, G+). Before: a squash conflict, or red checks after the plan branch moved, blocked the task (auto asked, yolo stopped).

### Rework, not block (`core/rebase.ts`, `core/close.closeTask`)
- Before every squash a trial merge (`git merge-tree --write-tree`, git ≥ 2.38) of the plan tip and the reviewed commit. A conflict, a failed squash, or red verify checks on the squash commit send the task back to the **same worker**: under `git.op` the mod checks out the task branch and merges the plan tip into it (`--no-ff`), leaving conflict markers in the worker's tree; a conflicted *locked* spec test keeps this task's version. The machine rewinds review·merge → active·worker (`rewind` is now legal from `review`), `cadre.base` becomes the plan tip (the review diff and the next squash show only the task's own change), `cadre.review` is cleared, `cadre.rebase` counts the round. The worker gets a queued resume naming the tasks that landed (from their `Refs:` trailers) and the conflicting files or the failing check; with no bound worker, main's card says to spawn it and the rebind handoff takes over.
- Then the ordinary gates: green → **re-review** (the reviewer is resumed: the code changed) → squash.
- Cap: 2 rounds. Past it the task is blocked with flag `conflict`/`merge-red`, and a dialog shows both sides (the other tasks and the files) with Retry (one more round) and Cancel task. Every round is recorded (`drive.decided` kind `rebase` + a beads decision).
- After each successful squash every running worker (active·worker) gets the new tip merged into its branch: in a throwaway worktree, then a CAS on its branch and `read-tree -m -u` on its live tree (its uncommitted edits stay; a clash leaves its tree and ref alone). A sibling that would conflict only gets a heads-up; its own merge reworks it.
- Early warning (`rebase.watch`, from the 5 s tick every 60 s): a trial merge between every pair of running workers' trees (`git stash create` includes uncommitted edits); a collision tells both workers once. On git < 2.38 the declared paths are compared instead.

### Prevent: paths, a thin core first (`core/validate`, `native/tasks`, `policy/guards`)
- Task metadata `paths` (files/folders it changes), `core` (bool), plan metadata `notes`. With two or more code tasks every task must declare `paths`; two tasks whose paths overlap (equal, folder, glob) and that no `blocks`/`waits-for` chain orders are in the plan's "missing" list ("move it into one core task or add a blocks dependency"), so the draft goes back to the planner and the approval is refused. Rejected: requiring a written reason on the dependency (TaskUpdate has no field for it).
- When the core task lands, its changed files are locked for every other task of the plan (`policy.core`, set at the core's close and at each later claim): the fence denies an edit with "report outcome blocked with the change you need", and a worker report touching them is refused. The change then becomes a core-patch task by the usual plan amendment.
- Briefs carry the plan's `notes` (one shared exploration before the fan-out) and the declared paths of the other running tasks.
- Planner rules (still ≤ 1.5 KB): vertical slices (demonstrable alone, one fresh context, own wiring + one smoke assertion), paths, a thin core task first, one shared exploration whose findings go in `notes`.

### Failure baseline (`core/tdd.oldFailure`, generalises knownRed)
A check that was red when the plan started gates only on NEW failures. Measured lazily the first time a check fails (no cost while everything is green), at `merge-base(plan branch, dev)` in a throwaway worktree, once per plan and check (epic meta `cadre.baseline`). With a JUnit report the signatures are the failing test names: any failure not in the baseline fails the gate. Without a report a check that was red at the start counts as old (as weak as knownRed; noted). Integration skips a check that was red at the start (the tasks' green gates guard new failures).

### A task waiting on the human parks (`core/drive.gate`)
Before: any blocked task paused auto and stopped yolo for the whole plan. Now a blocked task holds the run only when nothing else can move (no active/review/todo task outside the blocked ones and their dependants); otherwise drive keeps sending `Continue: <next>` and main's next line says "<id> waits for the user (go on with the rest)". Git flags and plan flags still hold at once.
