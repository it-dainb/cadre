# ADR 0007 — `/cadre setup` and `/cadre doctor`

Status: accepted (user request, post-v1). Adds two subcommands to DESIGN §5.3.

## Why separate from `/cadre init`
`init` is per project (repo, store, discovery, containment); it assumes the machine is fit. `setup` verifies the machine and user once: Claude Code build, `git`, `bd` >= 1.3.0, `bwrap` (overlay needs >= 0.11) with a working user namespace, `socat` (the Claude sandbox needs it on Linux), a writable worktree root, and the user-level env cadre relies on (`CLAUDE_CODE_ENABLE_TODO_TOOLS`). Results (ADR 0001): bd 1.3.1 lacks `--if-revision`, bwrap < 0.11 means copy-jail, macOS has no bwrap.
`doctor` is the read-only half: the same machine rows plus project rows (init stages, containment, beads and journal, branches, expired leases, flags, quarantined refs, queued resumes, sync ping with a 5 s timeout, drive). It is idempotent, makes no writes, and anyone may run it.

## Setup runs the user-level fixes after one confirm (changed from "never auto-install")
First version only printed commands. A real install showed that defeats the point: the human had to copy five fixes by hand. `/cadre setup` is now preflight, plan, one confirm, execute.
1. Preflight: the machine checks plus the user-settings diff.
2. Plan: every fix cadre can make with no password becomes an ordered action run through `h.run`, outside the Claude sandbox: `npm install -g @beads/bd@latest` (else the official beads install script via curl, which installs without sudo), the user-settings merge (`.bak`, re-read), `mkdir -p` of a missing worktree root. Anything needing root (`sudo apt install bubblewrap socat`, AppArmor, sysctl) is never run: it is listed under "you run once" with the fix for the detected cause. The plan is shown in the pane (Doctor tab, "Setup plan"); the command text is `setup: 2 actions ready · confirm with the code on the band`.
3. Confirm: `/cadre setup confirm <code>` (stage key 90, nonce-salted, burn-on-use) is bound to a hash of the exact plan (actions plus the settings diff and old bytes). A wrong code is burned; a plan that changed since it was shown is re-planned with a fresh code and nothing runs.
4. Execute in order (npm gets 300 s), one short toast per step (`setup: installing bd`), pane rows with state; the first failure stops the run and shows the last 8 lines of its output in the pane. Then the preflight runs again and the report is final. The stamp (`$.store cadre:setup {cc, bd, bwrap, jail, at}`) is written only when nothing is CRIT and no action is left. Nothing to do: `setup: all ok` and stamp.
Why not sudo: the mod has no password and must not ask for one; a one-line `! sudo …` typed by the human is the honest boundary.

Diagnostics shared with `doctor` (read-only):
- bd shadowing: a stale `bd` (say `/usr/local/bin/bd` 0.43.0) can sit before the npm one. When `bd` is missing or old, the npm global prefix is probed; if a good bd is there but another path answers first, the row names both paths and the fix (remove the old one, or put the npm bin first in PATH) instead of reinstalling. After an install the re-check catches the same case, so success is never claimed while the old bd still wins.
- bwrap user namespace, real cause: `kernel.apparmor_restrict_unprivileged_userns=1` (Ubuntu 24.04+) gets the AppArmor profile for bwrap from the Claude Code sandboxing docs (`sudo tee /etc/apparmor.d/bwrap`, `systemctl reload apparmor`), with `sysctl -w kernel.apparmor_restrict_unprivileged_userns=0` plus `/etc/sysctl.d` as a quicker option that loosens it for every program, Claude Code's own sandbox included. `kernel.unprivileged_userns_clone` is suggested only when that file exists and reads 0 (Debian). Otherwise the row points at the docs.
- Claude Code build other than the pin: a WARN with no action. `newer than the tested 2.1.295; usually fine`. Never an npm reinstall: a second install would shadow the native one.

## Output rules (DESIGN D2, need-to-know)
The command `{text}` is model-visible, so it is one line (`setup: 1 fail, 2 warn — report in the cadre pane`, `doctor: all ok`) with no mechanism words (`tests/doctor.test.ts` runs the wording lint on it). The full report goes only to human surfaces: the pane tab `doctor` (`ui['doctor.rows']`, tags `[OK]/[WARN]/[CRIT]`, UI-DESIGN §6.0) and `$.ui.log`, one short line per row (never a multi-line string: the transcript shows newlines as U+FFFD).

## Known gap
The plugin's own version is not shown: a mod has no API for it, so the row is left out rather than guessed.

## Dormant until `/cadre init` (added after the first marketplace install)
A user-scoped install used to enforce in every repo: guards took Bash and Edit from main in unrelated projects. cadre is now per-repo opt-in: a repo is active only when `<repo>/.cadre/config.json` exists (init stage 1 writes it). `core/session.wake(h)` is the one check: active is cached in the session secret, dormant re-reads the file (one read), so `/cadre init` takes effect on the next hook without a restart. When the repo turns on, `wake` runs the session policy, the draw of the session token and the containment check once.
Dormant: every gating slot passes straight through (turn.complete, agent.spawn, tool.check, tool.call guard and wrap, tool.describe, session.send, prompt.submit, prompt.attachment, turn.step, session.compact, config.set, result-card render), the 5 s and 30 s timers do nothing, and no band or toast is drawn, and no setup nudge (the band only draws a pending init or setup code; the pane render stays on too, so `doctor` and `setup` can show their report). Still working: `/cadre setup|doctor|init|open`. Any other `/cadre` sub, `status` included, answers `cadre is off in this repo · run /cadre init`. Once active, the fail-closed handlers apply as before.

## Short toasts
A toast is one line of about 60 characters at most, detail in `/cadre doctor` or the pane: `cadre: containment degraded · /cadre doctor`, `cadre: N commands unsandboxed · /cadre doctor`; the drive/context/fresh-agent/spec-change/conflict toasts were shortened the same way.

## Live result (harness tui.sh, haiku, container without `bd` on PATH, `NPM_CONFIG_PREFIX` a user dir)
`/cadre setup` showed the plan (1 installing bd, 2 creating the worktree folder, 3 writing user settings) plus the `you run once: ! sudo apt install bubblewrap` line (bwrap 0.8.0 in the image); `/cadre setup confirm <band code>` ran the three steps (npm took about a minute), the pane marked each done, the re-check read `bd 1.3.1`, and the settings file gained the env. The userns-blocked case is not simulated live (the harness runs with seccomp and AppArmor unconfined so bwrap works); it is covered by kit tests only.

## 0.5.0: auto-fix more, hand the rest to main, sudo stays human
Feedback from a real machine: after confirming, the card still said "you run once: ! rm ~/.local/bin/bd", and setup felt like a logic check with no agent in it.
- More actions: a stale `bd` that shadows the good one in a folder under `$HOME` becomes `mv <path> <path>.cadre-old` (reversible, never `rm`); the re-check then sees which `bd` wins. In a system folder there is no action, only the `sudo rm` line (or put the npm bin first in PATH). A stale `bd` with no good one yet gets install, then the move (unless the npm prefix is that same folder).
- Agentic step: after the confirmed actions, any CRIT row without a `sudo` fix, or a failed action, is handed to main as ONE prompt (`brief`: the failing checks with evidence, the goal, "no sudo, never touch the Claude Code install, user-level fixes, move aside instead of delete, say what you changed", "stop when done; the checks run again on their own"; the need-to-know lint passes, home paths shown as `~`). The card reads "Claude is fixing setup… (n issues)". When main's turn ends, `afterFix` (an ungated turn.complete registration) re-runs the preflight, redraws the card and stamps if nothing is CRIT. One hand-off per `/cadre setup` run (`secret.setupFix` is cleared first, so the re-check never hands off again).
- How the prompt is sent: `$.prompt.submit` is refused while a `command.run` holds the turn (PC-05), so it goes from the button press (no hook holds a turn; G6: our own hooks do not see that call, which is fine). If it is refused anyway (the typed `/cadre setup confirm`), the brief is kept in `secret.setupFix.text` and sent at the next main turn.complete. Not awaited: the call resolves only when its turn starts.
- Dormant only: in an active cadre repo main has no shell (guards), so setup runs the scripted actions only and the card says "Open Claude in another folder to let it fix the rest". The re-check runs only at the end of the turn the hand-off started: `turn.start` marks it (`secret.setupFix.turn`; the engine passes a plugin message as `The cadre plugin sent a message:\n<brief>`, so the marker is the stored brief contained in the turn text, or an empty text; a press's own `$.prompt.submit` is invisible to our prompt.submit hook, G6, but turn.start is the engine's own event). A turn that was already running when the brief was queued ends without a re-check. At that turn's end, `afterFix` first runs the scripted actions the stop-on-failure left undone (worktree folder, settings merge), then re-checks.
- Sudo is never automated: no password is available and `! sudo` typed inside Claude cannot prompt for one. The card lists the lines under "Run in a terminal (needs your password)" (AppArmor profile first, the sysctl alternatives second) with [r] Re-check.
- Noise: `$.ui.log` gets one summary line per setup/doctor run, not one per row; the pane holds the report.
- Buttons are the ask/settle card (id `init:90`): [a] Fix all (`setup confirm {code}`, the existing plan-hash bound code), [r] Re-check (`setup`), [x] Cancel (`setup cancel`).
Live (harness tui.sh, haiku): (A) stale `~/.local/bin/bd` 0.43.0 + good bd in `/usr/local/bin`: [a] moved it to `bd.cadre-old`, `bd` then answers 1.3.1; one log line. (C) no bd anywhere, user `~/.npmrc` pointing the npm prefix at a root-owned folder: the install failed, main was asked, set a user prefix, installed bd, and the automatic re-check showed `[OK] bd 1.3.1`. Evidence stays local (`/tmp/cadre-tui`), not committed.

Harness: `harness/check.sh` (sourced by run.sh and tui.sh) refuses to start when the image lacks the label `cadre.harness.home=/cchome`, with the rebuild command; the Dockerfile sets `HOME=/cchome`. Live case C re-run on the rebuilt image: clean start, no login prompt, main fixed the npm prefix, the auto re-check at the end of that turn ran the skipped settings action and showed `[OK] bd 1.3.1`.

## 0.5.1: human-run fixes are scripts; the card shows one short line
Bug from a real machine: the card printed the sudo commands inside the `║` border, hard-wrapped, and three alternatives together. Pasted into a terminal they gave `║: command not found` and broken quoting.
- Every human-run fix (AppArmor profile, `userns_clone`, `sudo rm` of a system-dir bd shadow, apt/brew installs of git, bubblewrap, socat) is a script `<cache>/cadre/fix/<name>.sh` (`$XDG_CACHE_HOME` or `~/.cache`): mode 0700, `#!/bin/sh`, a header saying what and why, `set -eu`, the exact command (no inner `sudo`: the script runs as root). Only setup writes them (no confirm: harmless until the human runs them); doctor stays read-only and shows the line only when the script already exists, else `run /cadre setup to prepare the fix`. If a write (or the chmod) fails, no path to a missing file is shown: the card/pane say `couldn't write the fix script (<reason>); the exact command is in the cadre log`, the whole fix is ONE unwrapped `$.ui.log` line (`fix command: sudo sh -c '…'`, steps joined with `&&`, quotes escaped) and [y] copies that command instead.
- Card, pane and row text show ONE line per fix: `sudo sh ~/.cache/cadre/fix/<name>.sh` (the `~` form when the folder is under `$HOME`; the shell expands it on paste). macOS installs run `sh …` without sudo (brew refuses root).
- Only the recommended fix is a command. The AppArmor alternatives (the two sysctl variants, less safe: they loosen user namespaces for every program) live in `fix/README`; the card carries one note line, `less safe options: ~/.cache/cadre/fix/README`.
- A command line is never wrapped inside the box: the lines are short by construction (names are short) and, if one still exceeds the body width, `ui/card` drops the `sudo sh ` and shows the script path alone. Test: at 56 and 116 columns every drawn command row is one unwrapped row with no box character inside.
- Copy: the 2.1.295 API has a clipboard (`$.ui.copy`, UI-31), so the card gets `[y] Copy command` (`setup copy`, verb change): it copies the short line of the first pending sudo fix and the toast says `copied` (`not copied: select the line in the card` when the terminal has no clipboard). Shown only when `Host.ops.copy` exists and a sudo line is pending. No surface is passed (a press path has none to pass); the session's first surface is used.
- [r] Re-check is unchanged: once the human ran the script the probe passes, the row turns green and the card clears (tested by flipping the machine fixture).
Live: AppArmor cannot be simulated in the harness (it runs unconfined), so this is kit-tested only; the card was not captured live.

## 0.5.2
bwrap < 0.11 (e.g. Ubuntu 24.04 ships 0.9) has no overlay: the copy jail is a supported mode, so setup/doctor report it as OK with no sudo step. Asking for an upgrade the distro cannot provide left an unsatisfiable "needs you" card.
