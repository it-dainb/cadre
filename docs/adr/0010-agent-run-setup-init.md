# ADR 0010: agent-run `/cadre setup` and `/cadre init`

Status: accepted (0.7.0). Supersedes the mod-run parts of ADR 0007 (setup actions, confirm code, copy) and ADR 0009 (staged init, auto-advance, agentic hand-offs, resume). Kept from both: dormant until init, one-line command text, need-to-know wording, decision cards, sudo stays human, git identity asked and never made up.

## Why (real machine, 0.6.1)
1. Init stuck at step 4: the explorer finished, main summarized the discovery in chat, and the card still said `init 4/8 discovery · Claude is on it`.
2. Setup and init ran inside the mod (`h.run`): the user could not see what was being installed or run. They wanted what omc-setup does: the agent does the work in the open (visible tool calls, spinner, timer), fully automatic.

## Step 4 root cause
Stage 4 waited on `ui.discoveryAgent`, set by admission when it retyped the spawn as the discovery explorer, and cleared only by an accepted `report{discovery}`. The explorer is unbound, so close.observe never nudged it or auto-reported for it. When it stopped without an accepted report (a text answer, or a report refused by validation), `init.after(end=true)` saw `discoveryAgent` and returned early ("still running"). Every later `after(end=false)` needed `moved` (a stored report). Nothing could clear the state, so the card stayed "Claude is on it" forever. Underneath that: the explorer was unbound, so its stop was never observed (no nudge) and main got its raw text instead of a card (see "One output contract"). It reproduced in the kit at 0.6.1 HEAD: run init to stage 4, admission spawns `ag1`, then `afterFix` for turns t1, t2 and t3. The regression test (`tests/init.test.ts`, "regression: main answers in chat …") now covers the same situation in the new flow. Nothing waits on an agent any more. The state is the files, re-checked at every main turn end.

## One output contract for every agent
The user saw the discovery explorer finish in 46 s without calling report, and main then got its raw text. A mod cannot block a subagent's stop here: `classic.SubagentStop` (AG-21) is skipped under the managed guard (`cc-plugin-sec-default` judged cadre in the user's log), and P3 bans `classic.*` anyway. So the rule "an agent cannot hand back until its output is valid; main gets only concise, controlled output" is enforced with what does work, for every cadre agent kind:
1. **Tracked from admission.** Task agents (worker, tester, reviewer, spike explorer) are bound as before. A marker-less explorer (an "ask", which is what the discovery explorer was) has no task, so it now goes into its own table (`core/asks`, `ui.asks[agentId]`: id `ask-<6>`, the question, the Agent `tool_use_id`, nudges, answer). It is not put in the binding table because a binding's `taskId` is a store id everywhere (heartbeat, resume lease, prune). That was the hole behind step 4: no binding, so no nudge and no card.
2. **Stop without a valid report:** the SAME agentId is resumed through the queued resume with a short nudge carrying the schema's example, at most twice. Then it is auto-reported. An ask or spike explorer is auto-reported as its final text trimmed to 2000 characters, flagged `auto-reported`. A worker is auto-reported from computed facts as before.
3. **Main never receives an agent's free text.** The foreground Agent result (tool.call wrap, S39) and the background task-notification (prompt.submit `task-notification`, S40) become the card for all cadre agents, asks included. The ask card has the role, its status (`answered (n citations)` or `finishing its answer`), flags, one line of the answer (at most 200 characters) and `next: full answer: TaskGet ask-…`. TaskGet answers `ask-…` ids from the table. If the card said "finishing", the answer card is sent to main once when the ask reports or is auto-reported (from its turn end). A later notification for it says only that it was given.
4. **The report tool stays the gate:** envelope errors carry an example and the agent retries in the same turn. An ask that reports under another role is refused with the explorer example.
Kit: `tests/asks.test.ts` covers the nudge ×2 with the example, the auto-report, the foreground card, the single late answer, the background card (no `<result>`, no prose beyond the 200-character line, wording lint), TaskGet, and the role refusal.

## Decision
- **Claude does the work.** `/cadre setup|init` (human origin only, `core/dispatch.needsHuman`) answers one line (`init: Claude is on it · progress on the cadre card`) and hands main ONE short brief: `Set up cadre in this project. Follow <plugin root>/guides/init.md step by step.` The root is `$.plugin.root` (`Host.root`), computed at runtime; no absolute path is committed. `guides/setup.md` and `guides/init.md` list numbered phases like omc-setup: the exact Bash commands (checks, `npm install -g @beads/bd@latest`, `git init`/branch/exclude, `bd init …` and its config, the `.cadre/config.json` shape with the discovered packages, the KAC skeleton, the settings env merge with a `.bak`), when to use AskUserQuestion (git identity, mission goal/constraints/non-goals, "did you run it?" after a sudo line), and what "done" means per phase. Discovery is done by main itself (Read, `ls`, `cat`, `git ls-files`; Grep/Glob do not exist in this build). Init spawns no explorer.
- **cadre checks (commands/agentrun).** The checks are deterministic and read-only. Setup uses the machine rows plus the user-settings env. Init has one predicate per phase: repository, task store, mission, build and test commands, commands pass on a clean checkout, workflow, changelog, safety settings. At every main `turn.complete` while a run is active, cadre re-runs them and redraws the checklist card (`run:<kind>`, kind `init`, so the band draws it in a dormant repo too): `✓` done, `✗` Claude's to fix, `…` waits for the human, `·` after the steps above, `!` a warning that never blocks. If an item Claude owns still fails, cadre sends ONE follow-up naming the failing checks with their evidence, at most 3 per run. After that, or at the limits, the run ends and the card shows what is left with [r] Retry. When every check passes, the run ends, the card says `all done` with [x] Close, and setup writes its stamp.
- **The jail validation stays mod-run** (it is a check, not a setup action): each package's setup and checks run in a clean offline copy at HEAD (`discover.exec`, audit mode), cached per package list. A red or network-dependent check fails the row and goes back to Claude ("fix the command or leave it out"). knownRed is no longer proposed by init; it stays a user-level key a human sets.
- **Maintenance lease** (`policy/guards.leaseOf`): only after a composer- or press-origin `/cadre setup|init` (`secret.run`). While it is live, main may use Bash, may Write/Edit only `.cadre/**`, `.git/info/exclude` and the changelog (settings files and `~/.claude/cadre.json` were removed, see below), and may Read the guide's folder. Source files are never allowed. It ends on verified completion, cancel, 20 main turns or 30 minutes. Activation (`.cadre/config.json` appears mid-run) does not revoke it: the lease lives in the session secret, and `wake` only adds `active`. Known limit: Bash is not path-fenced. A command can write anywhere the OS lets it. The guide forbids source edits, and the lease is human-started and short.
- **Human gates that remain:** (a) the mission is approved on the existing plan-approval card (Claude drafts it with `TaskCreate{kind:"mission"}` and goes on without waiting). The approval re-checks the run (`dispatch.RUN.recheck`). (b) The safety settings: once everything else passes, cadre shows the diff (the `settings.local.json` sandbox block plus the cache folders the audit learned, and `~/.claude/cadre.json` `jailWritable`) on the `init:5` card. It writes them (with `.bak`, re-read, policy, contain) only after Confirm (nonce-salted code, burned on every attempt, refused when the files changed since the card). Gathering input with AskUserQuestion is not approving a gate.
- **sudo stays human.** Setup writes each root fix as a script under `~/.cache/cadre/fix/` (unchanged from 0.5.1). The checklist row and the follow-up carry the one short line. The guide tells Claude to give the user that line and to ask "Did you run it?" with AskUserQuestion. The next re-check sees the result.
- **Init 8 (sync) left init.** `/cadre sync add <adapter>` is unchanged and optional. `init 5 allowlist` is gone (no request for it since 0.4).

## Settings files are never written by a model (security, 0.7.0)
`~/.claude/settings.json` and `.claude/settings.local.json` hold permissions, hooks and the sandbox. A drifting model could add allow rules or turn the sandbox off, so they left the lease, and so did `~/.claude/cadre.json` (it holds S-class keys such as `jailWritable`, `knownRed` and strictness). The lease now covers only `.cadre/**`, `.git/info/exclude` and the changelog.
- **Applied by cadre after a card confirm.** Setup's env merge (`CLAUDE_CODE_ENABLE_TODO_TOOLS`) is the `init:91` card "setup · user settings · confirm": the diff, a nonce-salted code burned on every attempt, re-read and compared with the card, `.bak`. It works like init's safety settings card (`init:5`). The checklist row is `…` (waits for the human), never a failure Claude is asked to fix. The guides tell Claude never to edit a settings file and to ask the user to confirm the card.
- **Fence:** Edit/Write/NotebookEdit on any `.claude/settings*.json` is denied to every agent, lease or not, with "these settings are applied for you after you confirm the card". In a repo where cadre is off, the guards do not run. During a setup run there, `guards.settingsOnly` applies this one rule.
- **Change detection (L3-style, for Bash):** when a run starts, cadre keeps the bytes of both files (`secret.run.snap`). After each of its own confirmed writes it takes them again (`agentrun.resnap`). Every re-check compares them. Any other change stops the run, logs `cadre: settings-changed: …` and shows a CRIT card `settings-changed · <kind> stopped` with the JSON diff. [r] Restore writes the earlier bytes back and keeps the changed file as `<file>.cadre-changed`. [k] Keep accepts the change. Both are human-only (`/cadre setup|init restore|keep`).

## How the brief is sent (live finding)
`$.prompt.submit` is refused from a `command.run` or press frame, and `$.clock.after(1, …)` from inside a command inherits that frame. Live: `prompt.submit: called from a command.run hook, it would wait on the turn this hook is holding`. So the brief waits in the run (`secret.run.brief`) and goes out from the session's 5 s timer (`agentrun.pump`; rooted in session.start, after it returned, so SS-04 replay does not swallow it) or from main's turn end. It starts once the session is idle.

## Removed
Setup actions (`Act`, `runActs`, plan hash, `setup confirm|copy`, identity fields), the staged init (stages, `show`/auto-advance, `resume`, `blocked`), `decide.handOff`, `doctor.afterFix`/`turnStarted` (and the `turn.start` hook), the discovery explorer path (admission retype, `briefs.DISCOVERY`, the `next: spawn the discovery explorer` line, `report{discovery}`, `init.discovered`), `discover.brief`, the pane's "Setup plan" block, and `git.IDENT_FIELDS/identityArgs/setIdentity`. Core LOC fell from 4121 to 3829. The decision fields and resume contract (ADR 0009) stay in the decision mechanism; init and setup no longer use them.

## Tests (kit)
`tests/init.test.ts` covers: the command answers one line and queues a short brief (sent by the timer, not from the command); another origin starts nothing; turn-end re-checks, the bounded follow-ups, then Retry; human-only waits send nothing; completion ends the lease and shows Close; the limits; the safety card (nothing written before Confirm, a wrong code is burned, changed files are refused, `.bak`, caches, realpath); the lease (Bash and the setup files only during a run, source files denied, the guide readable, survives activation, expires, ends on cancel); the guides' wording; and the step-4 regression. `tests/doctor.test.ts` covers setup's checklist: no writes besides the fix scripts, identity asked, warn rows never block, the stamp.

## User-facing notes (for the README writer)
- `/cadre setup` (once per machine) and `/cadre init` (once per repo) are run by Claude, in the open: you see its Bash, Read and Write calls with the usual spinner and timer. It follows `guides/setup.md` / `guides/init.md`.
- A checklist card shows progress: ✓ done, ✗ Claude still fixing it, … waiting for you, · comes later. After each of Claude's turns cadre re-checks; anything still failing goes back to Claude by itself (up to 3 times), then the card offers Retry. A run ends when everything passes, on Cancel, or after 20 turns / 30 minutes.
- During a run Claude may run commands and edit only the setup files (`.cadre/`, `.git/info/exclude`, `CHANGELOG.md`), never your source and never a Claude Code settings file. Only a `/cadre setup|init` you type or press starts a run. If a settings file changes during a run anyway, the run stops and a card shows the change with Restore / Keep.
- What still needs you: answering Claude's questions (your git name and email if git has none, the project's goal, constraints and non-goals); approving the mission on its card; confirming the user settings card (setup) and the safety (sandbox) settings card (init), which cadre writes only after you confirm; and running any `sudo sh ~/.cache/cadre/fix/<name>.sh` line yourself in a terminal (Claude gives you the line and asks when you're done).
- Every agent's result reaches Claude as a short card, never as the agent's raw text; an agent that forgets to report is reminded twice, then its answer is recorded for it (flagged).
