# ADR 0031: cadre 2.0, a general workflow engine

Status: proposed (DRAFT). Source: plan `cadre-2.0` section 12. Slice 0 findings below; later slices append their own.

## Decision

cadre 2.0 is a general workflow engine. Pipeline, roles, gates, flags (with parametrized effects), delivery hooks and the landing provider are data in a closed-schema **profile** (layers built-in, user, repo; repo wins; a repo may ship `.cadre/profile.json` and `.cadre/modules/*`, loaded as-is with user-layer powers; credentials are user-only, D18). Today's behaviour ships as the default profile, except the listed behaviours. Gates read an exit code and an optional JUnit XML file at `$CADRE_JUNIT` (read in core by `core/junit.ts`, vendored `@xmldom/xmldom`); cadre never parses output text. Installs and helpers are removed; changelog, semver, tag and commit conventions, the PR flow and submodule landing leave core; decisions are structured `choice` keys; clean break from 1.x. The sync engine is `modules/sync.mjs`, run by core on the tick through the one module runner (D17); its results are applied in-process by `applySync`, with no dispatcher command.

## Drivers

1. Generality proven by docs and analysis profiles with no core change.
2. No silent default-profile regression.
3. Caps, 60 s tests, quota-bound live gates.

## Alternatives considered

- Spec-first rewrite: no incremental proof.
- Three releases: the owner chose one.
- Profile-as-code: arbitrary code in the workflow (principle 5).
- Delete-only plus primitives with no loader: cannot prove generality; kept as the S5 fallback (Option E).
- A denylist lint on model text: rejected, words are removed at the source.
- A results-adapter slot for many formats: rejected (D14); JUnit is the contract, other formats go through a converter or get exit-only red.
- Sync kept in core: rejected (D17). In-process adapter plugins: still rejected.
- A repo trust flow (hash pin, capabilities, bwrap for repo modules, advisory scan): drafted, then dropped by the owner (D18).
- A regex XML reader: rejected; a vendored zero-dependency parser instead (D13, D14).
- Exit-only red for tests that were declared: rejected, a runner that never ran would pass; declared tests with no results are `gate-error`.
- A regex lint by variable-name heuristic: rejected as evadable; an explicit file list instead.
- A VCS abstraction: not yet.

Accepted weaker mode: exit-only red remains for checks that declare no tests (`cover:'report'|'none'` types).

## Why chosen

Incremental extraction deletes high-flake domain code first, pins behaviour with state-transition transcripts, and makes the interpreter a thin, gated last layer.

## Behaviours that change (owner-approved list, plan 2.13, B1-B23)

Risk scoring (B9), `twinOf` (B10), count lanes (B11), the `accept:` text prefix (B4), submodule landing (B7), the built-in PR flow becomes a module (B8), the `lite+tdd` lane (B12), the per-epic changelog amend into the merge commit (B6), per-test red for runners without a JUnit report and the `errorOk`/`missing()` text rules (B1-B3), conventional branch prefix (B13), Gherkin/`S\d+` (B15), config keys (B16), `flag.resolved` emission (B17). Not "bit-for-bit".

## Accepted owner risk (D18, B23)

"Opening a repo with cadre runs that repo's profile hooks/modules with your user's permissions (network on where its slots say); only use cadre on repos you trust." Not mitigated; also in `docs/limitations.md`. Credentials are user-only keys; `credentialEnv` is not inherited into hook, provider or module env (hygiene, not a boundary: same-uid `/proc` reads and an unpinned repo tracker URL are inside the accepted risk; the user may pin `adapters.<name>.url`, D23).

## Consequences

Core about -1.1 KLOC net (7399 to about 6280; sync's lines relocate into about 340 module LOC, so core+modules+profiles about 7140); modules about 560 LOC (cap 640); vendored xmldom under its own line; profiles about 300 LOC (cap 350). Exceptions to "no text parsing": `limited()` and `modelRefusal` only (unless the S7 spike removes them). `request` and helpers gone; supersedes the install and helper parts of ADR 0023 and 0028. Init runs each unit's test check once as a JUnit probe (B18, store key `junit:<unit>`, Doctor row). `runner` is removed from init output; exit-only red for a "no" unit is visible in Doctor.

D16 adoption: a unit without a test check adopts the first structurally-red tester `run` argv (JUnit required, B19); probe state `none` until then; the argv is task data run in the jail.

ADR 0012 and sync apply: adapters still send no commands; core applies a schema-validated result file in-process (`applySync`, lease re-checked, ops carry `base`, validated partial results applied). ADR 0012 wording is updated in S8.

Option E rule: the S5 go/no-go is objective (non-empty S0 gap list after the real-script dry run, or S1-S4 net more than plan +150 LOC); B1-B3 and B14 are signed at S2 and ship in any 2.0 release; D12 covers S5 onward only.

Follow-ups: F8 a trust flow for repo profiles; F2 profile editing UI; F3 a second landing provider; F4 quality benches on non-code profiles; F5 per-repo `profile` init flow; F6 re-measure test wall times each release; F7 rename `SCENARIOS.md`/`INTERFACE.md`.

## Spike answers

1. **Profile loading.** Built-ins stay `.ts` consts; a plugin-dir JSON is readable only at run time. `h.root()` (`hooks/register.ts:130`, `$.plugin.root`) plus `h.readText` works (`core/lanes.ts:123` reads `guides/goal.md` this way). A static `import x from './x.json'` is refused by the loader: "is not named like code and was not loaded: a hooks module and the files it imports end in .ts, .tsx, .jsx, .js, .mjs, .cjs, .mts or .cts" (throwaway plugin under the job tmp dir, `claude plugin test`). The sync flag cache (plan 2.5) needs the default profile synchronously at import, so `profiles/default.ts` stays a const; `docs/profile.md` prints it as JSON.
2. **gh field names.** `gh pr view --json` accepts `state`, `reviewDecision`, `statusCheckRollup` (field list printed by `gh pr view --json` with no argument, gh 2.45.0). A read-only call, `gh pr view 14858 --repo cli/cli --json state,reviewDecision,statusCheckRollup`, returned `MERGED`, `APPROVED` and a 25-element array of `CheckRun` objects with keys `__typename completedAt conclusion detailsUrl name startedAt status workflowName`; conclusions seen `SUCCESS`, `SKIPPED`; an old PR (9000) returned `[]` (empty = no checks, confirmed). The `StatusContext` element shape (`context`, `state`) is from gh's source, not observed. New finding: gh 2.45.0 has **no `--json` on `gh pr checks`** (`unknown flag: --json`), so the 1.0.1 call at `integrate.ts:104` already needs a newer gh; the module on `pr view` has no such requirement.
3. **Regex hits.** Table below.
5. **Dry run.** Gap list below: six gaps, none a pipeline branch, all in report/field/type shape.
6. **`h.run` env.** `init.env` is **merged** over the session environment, not substituted. Host impl `hooks/register.ts:98` passes `{cwd, ...init}` straight to `$.process.run`; the kit's behaviour is "`process.env` merged with `init.env` (not extended further)" (claude-mods `docs/research/2.1.295-engine-internals.md:317`, extracted from the 2.1.295 binary). I could not re-extract it from the binary in budget (grep over 255 MB timed out) and ran no live test. Consequence for S6: `core/modrun.ts` must spawn through an `env -i` argv prefix (`['env','-i', 'K=V', ..., argv...]`) to get an allowlist; the plan's stated fallback, LOC holds. `h.spawn` (`$.process.spawn`, `register.ts:100`) passes no env at all today.
7. **Vendored CommonJS.** **Not importable as is; an ESM copy is required** (blocks S2: answered). Evidence, throwaway plugin with a `claude plugin test` run on harness `claude-2.1.299`: importing `lib/index.js` of the `@xmldom/xmldom` 0.9.12 tarball unmodified fails with `the file did not load: require is not defined`. The kit docs agree (claude-mods `docs/catalog/system-access.md` SA-25: no `require`; "all ES modules"; `.cjs` is still ES; at most 1 MiB per file and 8 MiB per import graph; "vendor (bundle) a library's source into the plugin as relative files"). A single ESM file produced by `esbuild@0.24.0 lib/index.js --bundle --format=esm --platform=neutral` (219 KB, `export default require_lib()`) loads and parses JUnit-shaped XML (`DOMParser`, `getElementsByTagName`, `getAttribute` pass). Fallback to adopt in S2: `core/vendor/xmldom/xmldom.mjs` (the one bundled file, default export, `import X from` then `X.DOMParser`), VENDOR.json recording the upstream version, tarball sha and the exact esbuild command; imported only by `core/junit.ts`. Size 219 KB is far under the 1 MiB file cap; the budget line must count it separately.
