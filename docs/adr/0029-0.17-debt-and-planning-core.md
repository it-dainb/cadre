# ADR 0029: 0.17 live-fix debt, then the reduced planning core

Status: in progress (slices land one by one; the release block is written at the tag). Plan: `.omc/plans/cadre-0.17.0.md`.

## Slice 1: shape refusals have their own per-task budget (R1)

- **Decision:** every report refusal carries a declared code (`core/validate` `reportRefusal`, `Refusal`): `shape` (an over-cap value, an unknown field, a wrong type, a bad envelope or `run` form) or `semantic` (the rest). Nothing reads message text. A shape refusal of a bound task agent is counted in `Budget.shapeRefusals` (per task, in the store, so it survives a respawn and `/clear`) and never steps `report.refused`, so it never feeds the run's 3 tries. At `limits.shapeRetries` (default 6, 1..10) the task blocks through `blockTask` with the flag `shape`; the dialog offers Retry (resets the count, the agent starts again) and Cancel; Doctor has a row. The reviewer's lax-accept after `limits.reportRetries` now keys on the `semantic` code of the thrown `Refusal`, not on a regex over the message. Caps still reject and never truncate; unknown fields are still refused.
- **Asymmetry (accepted):** the shape count is per task, the semantic count per run. The planner's report path is unchanged: a planner has no task to charge.
- **Refusal text:** a quoted value or field name never carries a host path (`(a path)` replaces it).
- **Evidence:** the 0.16 live journals under `harness/out/matrix` hold about 477 refusals shaped like these across 230 agents (a text match over the saved transcripts, so approximate); the worst single agent met 7. Live runs showed workers and testers losing all three tries to a 122-155 character risk, a string where `followups` wants an object, or an unknown field, then being refused even for a valid report. The budget is therefore not precautionary.
- **Cell:** `shape-refusal-budget` (S): the worker sends four over-long reports, then a valid one; it lands and nothing blocks.

## Slice 2: the setup reply says only what the diff and package.json show

- **Decision:** when an install changed no manifest or lockfile, the reply (`core/helpers` `nothingToCommit`, `manifestNames`) says "Nothing changed in the manifest or the lockfile." plus the count of other files it discarded. Only for a readable package.json does it name packages: the keys of its `dependencies`, `devDependencies`, `optionalDependencies` and `peerDependencies` objects, so "package.json already lists X" or "X is not listed in package.json" is a true statement; every other manifest (pyproject, Cargo, go, Poetry) gets no claim about names, and a failed read means no claim. `uv pip install` never edits a manifest and says so. The scenario-prose half of the plan is dropped.
- **Names are untrusted text:** each is capped at 64 characters, a path-like or odd name is shown as "(a name)", at most 10 are listed ("and N more").
- **Cell:** `setup-stray-manifest` (S): the worker asks for the same install twice; the second reply says what package.json holds and never the old blanket claim.
## The specifier (slice 7, default off)
- **Decision:** role `specifier` (read-only; Read, inspect, report), `roles.specifier.enabled` false. One run per task before its claim writes how-to notes (`cadre.how`) for the worker only; the tester's brief template never reads them. Its report has no scenario field (an unknown field is refused) and one declared deviation kind (`none | wrong_path | scenario_conflict | missing_dep`), which shows the human one dialog; the task goes on as planned. It is tracked as an ask (core/asks), takes no task slot, and the claim waits while it runs (a run older than 10 min stops holding the task).
- **Side effect even when off:** the `report` tool's description and input schema gain the specifier's role and fields (`notes`, `deviation`) for every agent, because the schema is one fixed list (`additionalProperties: false`). The model-visible text of every agent's report tool therefore changed in 0.17 whether or not the specifier runs.
- **A1:** `fold-vs-keep` (L, `harness/matrix.sh release017`, RUNS=3 per arm, haiku, a two-epic milestone) and `node harness/fold-vs-keep.mjs`: the folded arm is worse iff it lands strictly fewer tasks, or lands the same and has at least 2 more rework+dialog events in total; worse turns the specifier on by default, anything else keeps it opt-in. The result goes here once run.

## Slice 4: explicit `holds`, and a spec_change always names its scenario

- **Decision:** a task may carry `metadata.holds: ["S2"]`, scenario ids whose behaviour already exists. Only the plan's author sets it (the plan tools; the tester and worker report schemas have no such field and are refused for their form). At plan time an id that is not a scenario of the task is refused (create, edit and the planner's batch). The red gate stays strict: a test named after a held scenario must PASS at red (the same run's JUnit statuses; no second run), every other test must fail, each held id needs a test named after it, and a task whose scenarios all hold needs no failing test. The mapping is the scenario id in the test name, the rule review coverage already uses. A change to `holds`, including removing an id, is an amendment-ledger entry like any approved field (original kept, once, then the user's). When a running task's base moves (`refresh`), the held tests are re-run on the merged tree; one that no longer passes blocks the task with the flag `holds` and a decision, it is never demoted to an unmarked scenario.
- **spec_change:** a report with that outcome and no scenario is refused next to the `reason` rule.
- **Prompt bytes:** the planner role prompt gains one line (64 B); the plan rules stay within 1536 B (other lines shortened); the tester brief gains one rule only when the task holds something (under 200 B).
- **Cell:** `holds-scenario` (S): S1 fails and S2 passes at red, and the task lands.
