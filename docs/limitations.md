# Out of scope and known limitations

## Out of scope (v1)
| Item | Why | Ever? |
|---|---|---|
| Parsing shell command text or stderr; deny lists of channels | Brittle; layers decide on effects, not text | never |
| Language/ecosystem presets in code | Stack specifics are discovered and validated config | never |
| Magic keywords, Stop-hook loops, `/goal`, statusLine HUD command, skills | One loop authority | never |
| Op-log sync queue | Sync is state-based reconciliation | never |
| Pane teammates, agent teams, workflow agents | Unseen or rewrite-proof | roadmap (in-process teammates) |
| Creating remote projects or custom fields | Admin actions; setup maps to what exists | roadmap flag |
| Everything on the DESIGN §15 roadmap line | Budget, YAGNI | roadmap |

cadre stops **model drift**, not the user: a user-tier mod can be switched off. It never pushes.

## Known limitations
From the M0 spike ([ADR 0001](docs/adr/0001-m0-results.md)):
- **PENDING-HUMAN smokes** (need an interactive TUI): S22 (background workers across `/clear`), S37 (`!` raises no `tool.call`), S48 interactive `/goal`, S49 trigger (`$.session.compact()` is unavailable headless, so the 60 % context hint is a toast, not an automatic compact). S41's MCP grant is rechecked at M3.
- **A restored `/goal` is undetectable** (S48, A27). After `/resume` with drive on, a one-time band hint appears. Do not combine a restored `/goal` with `/cadre drive on`: two loops would run. `/goal` typed in the session is observed as prompt text and pauses drive.
- **No bwrap overlay** (needs ≥ 0.11; hosts have 0.8/0.9). Checks run in a **copy-jail**: a throwaway copy of the worktree, writable, network off. The cache audit uses an empty scratch `HOME` listing.
- **bd 1.3.1 has no `--if-revision`.** Drive and sync leases live as metadata on the `cadre-control` issue, with read-check-write-reread (guarded by `--if-assignee/--if-status`). Drive continues after `/clear` (DESIGN §9).
- **Tester has Read/Write/Edit only** (this build exposes no Grep/Glob, S45); briefs name the paths. Plan B (ADR 0004) is not needed.
- **Headless (`-p`) runs end with main's turn** (a background agent is killed): spawn agents in the foreground. `plugin eval --allow-tools` refuses `mcp__*`: name `mcp__cadre__report mcp__cadre__inspect mcp__cadre__run_check`. Live results: [ADR 0005](docs/adr/0005-live-results.md).
- **`!` shell commands** in a human session may bypass the hooks (A20 unverified); the effect check treats such changes as human.
- **A stale explore intent can hold a goal stop.** A question queued for an explorer that never started stays queued, and the goal stop waits on it. No run has shown it fail, so it is a known limit, not a fix.
- **`human.retry` resets the rework count** (`core/lifecycle.reset`), so a task the human retried can read as first-try in the `/cadre timeline` metrics. A retry is itself a rework signal; no second counter is kept. Metrics history starts at 1.0 (no backfill); a task's start time is its first metered usage (run records carry no time).
- Per-repo state: the mod's policy (repo, worktree root, locks) is keyed per repo, so two repos in one user config do not share it.
- Workers cannot `git add/commit` (repo-level `denyWrite`, S24): the mod commits. `/tmp` is not writable for subagents; use `$TMPDIR`.
- Per-agent 1 h cache TTL needs plugin agent files and may be ignored on accounts without usage credits; cadre reads the usage fields to detect it.
- **Linux only.** On another OS (`uname -s` is not Linux) cadre logs one line, registers nothing and stays off.
- **Keep going has no restart cap.** An agent that keeps stopping (`attempts`, `no-report`, `stagnant`, `stale`, `loop`) is restarted on every Keep going; the human ends the loop with Cancel task.
- **Already holds is lost on a re-asked red dialog** after `/clear`: the passing ids are not stored, so the dialog comes back with Retry only.
- **Red and green read the check's exit code and, when the runner writes one, a JUnit report (2.0, B1-B3, B14, B18, B19).** cadre never reads test output text. A runner reports to `$CADRE_JUNIT` (cadre sets the path for each run). A test that errors instead of failing is not a red: the tester makes it compile and run (B1). With declared tests and no report, red and green stop as a gate error for the human, never as a red or a pass (B2, B3). A check that declares no tests (a type without a red step) is judged by its exit code alone: the accepted weaker mode, and "Already holds" is not offered without results. A check can write any report it likes, no worse than the exit code it already controls. `/cadre init` runs each unit's test check once and records whether it wrote valid JUnit (B18); a unit with no test check is written without one and the first test-driven task sets one up (B19: only a run that wrote valid JUnit and failed as red needs is adopted).
- **Decisions are structured (2.0, B4, B17).** A flag is answered by the option's key (the dialog, `/cadre resolve <id> <key>`, or main's `status {id, choice}` under yolo); the `accept:` / `reject:` text prefix is gone, and a `reason` is recorded, never read. An answer emits one `flag.resolved` per flag that left the task, so cancelling a task now closes its flags' events too.
- **Delivery hooks and landing modules run with the user's powers (2.0, B6, B8, B21).** A hook, a landing provider and a module run on the host through one runner (`core/modrun.ts`): an argument list, no shell, a fixed environment (`PATH`, `LANG`, `HOME`, `TMPDIR`, the two `CADRE_*` paths and the names the caller's `envPass` lists). That keeps a credential out of logs and input files; it is hygiene, not a boundary: a hook of the same user can read `/proc/<pid>/environ`. What a hook changes is committed by cadre after an audit against the fixed protected paths (`.git/`, `.cadre/`, `.claude/`, `.mcp.json`) and lands by CAS, never by the hook itself.
- **Task commits carry their changelog entry on the epic branch (2.0, B6).** Each closed task adds one `docs(changelog)` commit. In a milestone two epics both append to `CHANGELOG.md`: git merges the file with its union driver (the profile's `landing.union`) and the changelog module's next entry or release tidies the result, so the merge does not conflict. The union rule lives in the clone's `.git/info/attributes` (local, never committed), so your own `git merge` of those files in that clone keeps both sides' lines too.
- **A unit that is its own git repository (a submodule) is not landed (2.0, B7).** Init and integration refuse it with one line; a parent whose checks only read a submodule is fine.
- **Sync is a module, one run per due unit (2.0, B20, B22).** `modules/sync.mjs` runs at most once per unit per 30 s (unless a task transition wakes a target) with a 60 s wall and a 45 s self-deadline, then core applies its checked result in-process. Consequences: an events adapter hears about a change within 30 s (it was 5 s); a run stopped at its deadline or killed leaves its pushed tasks recorded and the cursor where it was, so the rest follows next cycle; a task edited while the module ran keeps its local value and the op is retried (Doctor says how many ops were stale); the lease is 120 s. Doctor shows the last result and its age and starts no adapter.
- **The repo layer is an accepted owner risk (2.0, D18, B23).** Opening a repo with cadre runs that repo's profile hooks and modules with your user's permissions (network on where its slots say); only use cadre on repos you trust. A repo may ship `.cadre/profile.json` and `.cadre/modules/*.mjs`; they load as they are, with no approval step, and the repo wins over the user layer on conflict. No mitigation work is planned. The routes it includes:
  1. A repo hook reads same-user processes' environment through `/proc/<pid>/environ`, so the environment allowlist of the runner is hygiene and no boundary.
  2. A repo `sync.<target>.url` (project data) can send a credentialed adapter's request to another host unless you pinned `adapters.<name>.url` in your user config; a differing repo url is refused only when you pinned one.
  3. A repo hook's `run[0]` may be any program (`node`, `sh`, a repo script, an absolute path), and `landing.provider` is an unconfined path too; only `${MODULES}/` paths are confined to `.cadre/modules/` (no absolute path, no `..`, no subfolder, no symlink out).
  4. The two repo files differ: `.cadre/profile.json` is loaded as it is with user-layer powers; `.cadre/config.json` keeps the 1.0.1 rule for its keys (a repo file may only tighten safety keys, user-only keys are ignored). An invalid `.cadre/profile.json` makes cadre dormant for that repo (Doctor and `/cadre profile` stay); there is no fallback to the layers below.
  Credentials (`adapters`, `credentialEnv`) are user-only keys: a repo file that names one is refused. A configured adapter's credential is passed to that adapter's own process and to no hook, provider or module.
- **Without bwrap, check and setup commands run unjailed (2.0).** With no `bwrap` the jail mode is `none` and the unit's check, setup and the tester's `run` commands run in the worktree with your permissions, as in 1.0.1. With bwrap they run inside the jail through a check slot the profile declares (a slot's `network` is a profile attribute: the default declares `setup` network-on and `test` offline). Doctor shows the missing bwrap.
- **Installs are the agent's own step (2.0, B5).** cadre no longer installs packages: a worker installs what its task needs in its own shell and the manifest and lockfile changes are part of the task; a spec reset does not replay them. There is no setup helper and no `request` outcome.
- **The vocabulary of a task is data, with three accepted differences (2.0, B10, B11, B15).** The same-title duplicate check is gone (a second task with the same title is allowed). The lane is the planner's declared `lane` (a person can override it); a task count no longer picks it. Acceptance items are `{id, text}` with any id of 1 to 16 characters (no space, `:` or line break, unique in the task) and any one-line text; the Given/When/Then form and `S<n>` ids are not enforced. `lite` means lite: a bug that needs a test first goes in the full lane (B12).
- **The risk of a task is the planner's word (2.0, B9).** Model routing and review depth read the task's declared `risk` (`light`, `standard`, `thorough`, `core`; absent is `standard`), not a score from the diff. Default routing therefore differs from 1.0.1 for tasks that the score had called light or thorough.
- **Two refusals read engine text (2.0, plan 2.10).** Everything cadre decides reads structured facts (exit codes, JUnit, the `choice` of a flag, ids), with two exceptions where the host gives no structured code: `drive.limited` (a usage or rate limit shows only in the answer text of a turn that ended with an error) and `queue.modelRefusal` (an agent that cannot start because of its model rejects with a message only). Each is one tagged line (`engine-text-exception`), `tests/budget.test.ts` asserts there are exactly these two, and neither reads model or task text.
- **A read-only step is followed only by a role step or the report gate (2.0).** The loader refuses a profile whose read-only step (a role with no workspace and no verdict) is followed by a check or the integrate gate: nothing is left to check there. A question type (`spike`) ends at its report gate; a profile such as `analysis` goes on to a working step.
- **`/cadre init` runs each unit's `test` check once (2.0, B18).** One extra test run per unit, in its jail, bounded by the slot's `timeoutS`; the structural fact (does it write JUnit, does it have tests) is shown at init end and in Doctor. A repo whose runner writes no JUnit gets a note, and red stays a gate error with declared tests until the runner writes a report (B19: a test command is adopted only after a structural red).
- **Config keys of 1.x are gone (2.0, B14, B16).** `types`, `tdd.*`, `review.*`, `lanes`, `suites`, `changelog`, `release`, `landing.review/remote`, `units[].setup`, `units[].tdd.report`, `tdd.collectErrors` and `roles.custom` are now the profile, `units[].checks` and `landing.*`. It is a clean break with no migration: an old key is reported as an unknown key. Branch names are `<prefix><id>-<slug>` from the type's `branch` (B13). Submodule landing is refused (B7).
- **Red without a JUnit report is exit-only (2.0, B2).** A check that declares no tests (a `test` task, or a type whose acceptance is covered by the reviewer's list) and writes no report is red when its exit code says so, and nothing more: cadre cannot tell which test failed or that it failed for the right reason, and "Already holds" is not offered. With declared tests and no report it is a gate error instead.
- **What a check or setup command can read (2.0 fix rounds, narrows 1.0.1).** Every jail starts with `bwrap --clearenv` and sets only `PATH`, `HOME`, `LANG`, `TMPDIR`, `CADRE_JUNIT` and the profile's `sandbox.env`; with `--unshare-pid --as-pid-1` its `/proc` shows only its own processes. So a credential in your session environment (an adapter's `credentialEnv`, a token) reaches neither a test nor a setup command, and a tester's `run` cannot print it back. The **offline jails** (the `test` slot, the init probe, adoption: where a tester's `run` and other task-data argv execute) also get an empty `$HOME` (a tmpfs over it): `~/.claude`, `~/.ssh` and the rest of the home are not there to read. Put back read-only, only so the command can start: each `PATH` entry under `$HOME` that is a `bin` folder (`~/.local/bin`, `~/.cargo/bin`), plus the version folder of a versioned toolchain (`~/.nvm/versions/node/v22` for its `bin`), never a folder right under `$HOME` such as `~/.local`, `~/.cargo` or `~/.claude`; a toolchain whose commands do not sit in a `bin` folder under your home (pyenv shims) does not start in a check: put it on `PATH` through a `bin` folder or install it outside the home. A `bin` folder that is a link is bound as its target, and the version-folder rule binds the folder above any `<dir>/<dir>/bin` you put on `PATH` (`~/.config/x/bin` binds `~/.config/x`): `PATH` is yours, so what it names is readable. Also put back: the worktree, the scratch and the configured cache folders. The **network-on `setup` slot keeps the real `$HOME`** (a package manager's caches live there): that is the remaining exposure. It runs the unit's own `checks.setup` argv, written by the repo or by init, never a tester's `run`; a setup command could read the home and use the network. A profile that declares `network: true` on the `test` slot runs a tester's `run` in that same jail (real `$HOME`, network on): keep `test` offline unless you trust every tester run. Something a setup or test relied on from your shell (a proxy variable, a registry token) must now be set in the unit's own files or in `sandbox.env`. With no bwrap nothing is jailed (above).
- **The plan-time refusal checks task paths only (2.0).** A task whose `paths` name a protected file is refused when it is planned. A task that names the file only in its acceptance text, or lists a file of the landed shared core, is not refused: its worker blocks and the human answers the flag.
