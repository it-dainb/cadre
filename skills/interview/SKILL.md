# interview

Ask only what you cannot determine yourself. Read the code first — a question whose answer is in the repo wastes a round trip and signals you did not look.

One question at a time. Target the thing that most changes what gets built, not the easiest thing to ask.

When the shape is settled, hand off to `plan`. The spec is written through the same path `plan` uses — `interview` is a way of arriving at a plan, not a second mechanism for writing one.

Stop asking when the remaining unknowns would not change the work. Perfect clarity is not the bar; enough to build the right thing is.
